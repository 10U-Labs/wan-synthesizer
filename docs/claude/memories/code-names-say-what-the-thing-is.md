# Code names say what the thing is

A name in the code is read far more often than it is written, and almost always by somebody who has not opened its definition and is not going to. So a class, function, variable or field is named such that a reader meeting it for the first time can say what it holds or what it does, in ordinary words, from the name alone. A name that only makes sense once somebody has explained it is a name doing no work, and there is nobody left to do the explaining: GitHub issue #116 deleted every docstring and comment on 2026-08-22, so the name carries the whole cost of the choice every time anyone reads a line that mentions it.

Name the thing the thing is. A class holding the sites in the backbone, the joins the operator pruned, the carrier fiber and the backup limit is named for those, not for the role it plays in somebody's mental picture of the calculation. `_DetourSubstrate` was the failure to avoid: nothing in the repository is a substrate, the word says only that other things stand on it, and a reader who grepped for it learned nothing they did not already know from the line they were reading. `RouteGround` was the same shape. Both carried careful docstrings explaining what they really were, which is the evidence that the names did not. They became `_DetourSearchInputs` and `PathProofInputs`, renamed by GitHub issue #61 on 2026-08-17 along with `PathUse` to `SynthesisPath`, `SynthesisPaths` to `InputFiles`, `MeshTargets` to `MeshRequirements` and `_GraphContext` to `SearchGraph`. `PathProofInputs` is in `synthesizer.ceiling` and is the one to open. `_DetourSearchInputs` is gone: GitHub issue #60 deleted the class the same day it was renamed, because `synthesizer.survivable.select_fiber` began selecting the fiber for a whole synthesis at once, which retired the detour search the class carried the inputs for. `SearchGraph` is gone again: GitHub issue #116 deleted it on 2026-08-22, because its six fields were copied one for one into `SynthesisInputs` fifteen lines later at the one place it was built, and `build_synthesis_inputs` in `synthesizer.synthesize` now returns those inputs directly.

Abstract filler nouns are where this usually goes wrong: substrate, ground, context, handle, use, spec, info, data, manager, helper, wrapper. They can be attached to anything, so they distinguish nothing. The list covers every name a reader meets, variables and parameters and fields as much as classes. `ground` in `diverse_path_bounds` in `synthesizer.strength` is the case that proves it. GitHub issue #61 renamed the class `RouteGround` to `PathProofInputs` on 2026-08-17, and renamed the parameter that receives one to `inputs` in the ten `synthesizer.ceiling` functions that take it. The local in `synthesizer.strength` stayed `ground` for the five days to 2026-08-22, because that sweep was hunting route, span, circuit, cable and chokepoint and went past a word spelled `ground`. Renaming it was the wrong fix and was rejected twice: every name offered had to stand for a bundle of arguments, and a bundle of arguments is not a thing in a backbone, so each candidate came out saying nothing. The local was deleted instead. `diverse_path_bounds` now calls `diverse_path_ceilings`, which `synthesizer.stages` already used and which that function had been writing out a second time. A value built on one line and read on the next does not need a name, and reaching for one is how a word like ground or proof gets attached to something that has no counterpart on the network. `path_uses` is the second case and much the larger one. GitHub issue #61 renamed the class `PathUse` to `SynthesisPath` on 2026-08-17 and stopped there. The field holding a list of them kept the banned word on `Synthesis` in `synthesizer.model` and on `SynthesisDraft` in `synthesizer.assemble`, so did the `"path_uses"` key `synthesis_payload` in `synthesizer.output` writes and `backbone_links` in `synthesizer.collections` reads back, so did the parameter on `failure_cities_per_path`, `paths_out_of` and `diverse_path_count` in `synthesizer.validation`, and so did every loop and comprehension variable that walks one. The type and the variable ended up disagreeing inside a single line: `_laid` in `synthesizer.backbone` built `min(use.path, use.path[::-1]): use for use in pinned` over a `list[SynthesisPath]`, and `use.path` reads as though a use had a path rather than being one. GitHub issue #135 renamed the field to `drawn_paths` and the variables to `drawn_path` on 2026-08-22, 46 spellings of `path_uses`, 13 of `path_use` and 127 of the bare `use`, over six modules in `src/` and seventeen files in `test/`. Deleting was not open the way it was for `ground`, because a synthesis mostly is this list, so the fix was the word the repository had when #135 landed: [say-peers-and-circuits](say-peers-and-circuits.md) required path that day and has required circuit since, so `drawn_paths` and `drawn_path` are renamed in turn and are written as they are spelled until they are. The variable is `drawn_path` and not the bare `drawn`, which `synthesizer.backbone` had already given to a `_DrawnFiber` in seven signatures. Where a class genuinely bundles several things because they travel together, name it for what the bundle is for — the inputs a search reads, the limits a tenant set, the fiber a synthesis ordered — in words a network engineer would use without being taught them.

Plain English also means no computer-science vocabulary where a network word exists. This repository syntheses backbones. Its readers are network engineers. Prefer the word they already have, and take the words for the parts of a backbone from [say-peers-and-circuits](say-peers-and-circuits.md), which also bans path, route, span, cable and chokepoint as words for them — in identifiers as well as in prose.

Abbreviations are allowed only where the abbreviation is the ordinary form. `PoP`, `WAN` and `id` are ordinary. `cfg`, `res`, `tmp`, `idx`, `pt` and single letters are not, except as a loop variable whose whole life is two lines. Length is not the cost being minimised; a name six characters longer that removes a question is a saving.

Two checks that catch most of it. First, read the name in a sentence saying what it is — "this is the fiber a detour search reads" — and ask whether the name would have produced that sentence in the reader's head. Second, write out the one line you would have put beside the definition when this repository still allowed prose there, and ask whether it and the name say the same thing; if they do, the name is right, and if the line is a correction, the name is wrong. The line is thrown away — GitHub issue #116 deleted every docstring and comment on 2026-08-22 and there is nowhere to put it — and writing it is only a way of hearing what the name does not say.

This applies to new code as it is written and to old code as it is touched. Nothing mechanical checks it: whether a name says what the thing is cannot be read off the name by a program, and `lib/python/test_naming_conventions` was deleted by GitHub issue #55 for being 129 lines nothing imported. It is caught by reading.

This was written on 2026-08-17, after a session settled the vocabulary for prose and the user asked for the same standard in the code: names must be intuitive and self-explanatory, not obscure. Naming things by their exact names when writing *about* the repository is the neighbouring rule, in [write-the-exact-name](write-the-exact-name.md); leading with what a thing is for, before its identifier, is [lead-with-what-it-is-for](lead-with-what-it-is-for.md).
